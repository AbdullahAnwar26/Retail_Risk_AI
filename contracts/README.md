## Rules built into the contract

- **No credit-decision type.** `RecommendationKind` is a closed list: `PRODUCT_SUGGESTION`, `SERVICE_SUGGESTION`, `EDUCATIONAL_CONTENT`, `CREDIT_REFERRAL` (referral to the credit platform only; no eligibility, limit, rate or likelihood). No event type for credit decisions exists.
- **Purpose limitation (IC7, DEC-42).** Every JSON body, including errors, requires `not_for_credit_decisioning: true`; every response carries the header `X-Not-For-Credit-Decisioning: true`; customer-level bodies and customer-outcome events also carry `permitted_use: [RETAIL_INSIGHT, MARKETING_SUGGESTION]`.
- **Policy out (IC4).** Customer-level responses carry `policy.decision_id` (the decision-log id), `bundle_state`, `packs_applied` (pack versions applied), `effective_bundle_sha256`, obligations and flags; composite sections carry their own `decision_id`.
- **Illustrative watermark (DEC-44).** `illustrative` and `watermark` are required on every body and event payload; the schema ties `illustrative: true` to the fixed watermark text.
- **Market-neutral (two tracks, DEC-50/DEC-51).** Jurisdiction codes, consent purposes (AD-17), activities, reason/segment/need/playbook codes, track and cell codes are pattern-checked reference data, listed by `GET /v1/capabilities`, never contract enums. Example codes (`US-NY-NYC`, `AE-DU`) are illustrative only. One contract serves Track A (conventional, cells `A-US`, `A-UK`) and Track B (Islamic, cell `B-AE`).
- **Deployment profile, read-only (DEC-61).** `GET /v1/capabilities` returns `deployment_profile` (track, `institution_type` CONVENTIONAL / ISLAMIC, cell, currencies, locales, catalogue, institution overlay); decision and audit records carry `profile_id`, `track`, `institution_type`, `cell_id`. No request can set or override them.
- **Purpose-bound customer directory (DEC-68, contract 1.2.0).** `GET /v1/customer-directory` (`ri.customers.list`, analyst and relationship staff only) needs a registered `access_purpose` from a closed list, an exact token lookup or a narrowing filter, and stays within page 25, query total 100 and per-user quotas; every call, allowed or denied, writes an audit record with an access block (`AccessAuditDetail`). Denials: `ACCESS_PURPOSE_INVALID` (400), `ACCESS_PURPOSE_NOT_REGISTERED` (403), `NARROWING_FILTER_REQUIRED` (400), `ACCESS_QUOTA_EXCEEDED` (429), `FORBIDDEN_SCOPE` (403). `GET /v1/customers` is deprecated and not implemented.
- **Least-data dashboard reads (DEC-62).** The customer list returns tokens and coarse codes only (now through the directory above); `GET /v1/customers/{customer_token}/transactions` needs the purpose-bound scope `ri.transactions.read` and purpose `INSIGHT` and returns no raw description, counterparty or merchant name; `GET /v1/portfolio/summary` (`ri.portfolio.read`) is aggregate-only with small-cell suppression.
- **Sharia approval (DEC-55).** `POST /v1/policy/packs/{pack_id}/{version}/sharia-approvals` (`ri.sharia.approve`, ISLAMIC deployments only) records the Sharia decision on policies, catalogue items and templates; a Track B pack needs legal and Sharia approval. No user holds the scope until DEC-63 records a named person.
- **Sharia disclosure (file 20 SDC-11, contract 1.2.0).** In `ISLAMIC` deployments every `PRODUCT_SUGGESTION` and `CREDIT_REFERRAL` carries `sharia_disclosure` (Sharia basis, ISSC approval, certificate and KFS references per locale, contract type); `CONVENTIONAL` responses never carry it (`institution_type` on the response decides). Outside an `ILLUSTRATIVE` bundle only the approved shape is valid (`sharia_status: SHARIA_APPROVED` with `sharia_approval_ref` and `issc_approval_ref`); the demo shape carries `illustrative_sharia_assumption` and "illustrative - not a Sharia ruling" and no approval reference. The disclosure schemas are `GOVERNANCE` (Sharia approval values are allow-listed governance values).
- **Output classes.** Every schema that leaves the system is tagged `x-ri-output-class`: `CUSTOMER_OUTCOME` (scanned by the forbidden-term linter, planning/15 §3.3), `GOVERNANCE` (allow-listed: pack/policy approval values, model registry `APPROVED`, Sharia approval status and references), `OPERATIONAL`, `INPUT`. The linter must exempt the label `not_for_credit_decisioning` itself.

## Versioning

- SemVer `MAJOR.MINOR.PATCH` in `info.version`; the major is in the path (`/v1`). Every response echoes `contract_version` and `X-Contract-Version`; every event carries `contractversion`. Hosts may pin a minor with `X-Contract-Version` (unserved pin: 412).
- **Minor (compatible):** new optional request fields, new response fields, new endpoints, new values of fields marked `x-extensible-enum` (consumers must tolerate unknown values and unknown fields).
- **Major (breaking):** removing or renaming fields, changing types or meaning, making optional fields required, tightening validation, changing error codes, adding a value to a closed `enum` used in requests.
- Deprecation via `Deprecation` and `Sunset` headers; `/v2` served alongside `/v1` for at least 6 months [ASSUMPTION, DEC-31].
- Pack, model, catalogue and config versions are separate axes and never change the contract.
- CI gates (from the first endpoint story): Redocly lint, OpenAPI breaking-change diff (e.g. oasdiff) against the last released tag, forbidden-term linter over `CUSTOMER_OUTCOME` schemas and event schemas, example validation.

## How to lint

Run the validator from a scratch folder, never installing into the project:

```sh
# from an empty scratch directory, with the npm cache redirected there
export npm_config_cache="$PWD/npmcache" REDOCLY_TELEMETRY=off
npx --yes @redocly/cli@1.34.5 lint <repo>/contracts/openapi/retail-intelligence-v1.yaml --config <repo>/contracts/redocly.yaml
```

Expected result: `Your API description is valid` with no errors or warnings. Keep `allowAdditionalProperties: true` on `no-invalid-media-type-examples`: its strict mode injects `unevaluatedProperties` into each `allOf` member and rejects valid composed examples.

Event schemas: validate each file against the JSON Schema 2020-12 metaschema and validate its `examples` with all files of `events/` loaded into one registry (any 2020-12 validator, e.g. Python `jsonschema` 4.x with `referencing`).
